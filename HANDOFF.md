# HomeInventory Handoff

## Product Goal

Build a local-first iPhone inventory app that turns home walkthroughs, photo sweeps, and eventually a live camera stream into an assistant-ready catalog of individual belongings. The assistant should later use this data for cooking, restocking, organizing, and finding where things are.

The key user expectation is object-level inventory entries, not broad image categories. Each saved item should have a crop/photo, name, category, room/area/container, confidence, condition when possible, OCR/barcode metadata, and a flag for detail scans or laptop review when the phone cannot resolve it.

## Current State

- Native SwiftUI iOS app in `Inventory/`.
- Project generated by XcodeGen from `project.yml`.
- Uses `UltralyticsYOLO` Swift package from `https://github.com/ultralytics/yolo-ios-app.git`.
- Supports photo sweeps, video import/recording, manual item entry, review-before-save, local JSON persistence, inventory search/filtering, assistant snapshot export, and laptop review package export.
- In-app photo capture uses a custom `AVCaptureSession` camera and does not save source photos to Photos. Each shutter tap starts analysis automatically.
- Imported photos also auto-analyze. The old explicit photo review/analyze step is gone.
- Source videos/photos are treated as temporary; only object crops and reviewed inventory records are meant to persist.
- Motion samples are attached to in-app photo captures so nearby viewpoints can help deduplicate later.
- OCR/barcodes are used as corroborating evidence, not as a linear fallback that names random OCR fragments as items.
- Generic labels such as `cord`, `material`, `currency`, `container`, and `appliance` are treated as weak evidence or `Unidentified item`.

## Important Limitation

The current fallback detector is still the official generic `yolo26n` Core ML model:

`https://github.com/ultralytics/yolo-ios-app/releases/download/v8.3.0/yolo26n.mlpackage.zip`

That model is closed-vocabulary. App-side keyword lists cannot make it detect labels that were not baked into the model. For example, adding `spray paint` to a Swift list can help categorize OCR text after a crop exists, but it will not make `yolo26n` see spray paint as its own object class.

Before using that fallback, the app now looks for a bundled or app-container local Core ML detector named `inventory-yolo`, `yoloe-inventory`, `yoloworld-inventory`, or `home-inventory-yolo` with extension `.mlmodelc` or `.mlpackage`. Drop/export the proper inventory/open-vocabulary model under one of those names and both live and static scan paths should pick it up.

Room/mission selection should only bias metadata after detection. It is not the right place to fix missed objects. If the app only works when the user pre-declares `Toolbox` or `Pantry`, the UX has already failed.

## Recommended Next Architecture

1. Use a live camera scan as the primary UX.
2. Run real-time YOLO detection from the camera stream with `YOLOView`/`YOLOCamera`.
3. Replace `yolo26n` with an inventory-capable open-vocabulary or custom model:
   - YOLOE / YOLO-World style Core ML export with a broad home-inventory vocabulary, or
   - a custom fine-tuned YOLO model for household objects, plus a second-stage VLM/classifier on crops.
4. Track boxes across frames.
5. Draw stateful overlays:
   - gray/blue: object candidate seen
   - yellow: stable isolated crop, needs better identity
   - green: identity is confident enough to save/propose
6. Run OCR/barcode on stable crops to corroborate labels, brands, serials, expiry dates, and product text.
7. Save only object crops and item records, not source photo/video files.
8. Export tricky/low-confidence crops for a laptop or desktop VLM pass.

## Key Files

- `Inventory/Views/ScanVideoView.swift`: scan UI, photo/video analysis flow, proposal merging, next live-scan UI.
- `Inventory/Support/PhotoCameraPicker.swift`: custom in-app still camera with motion sampling.
- `Inventory/Support/VideoInventoryAnalyzer.swift`: static photo/video analysis, YOLO crop extraction, Vision OCR/barcode, grouping.
- `Inventory/Support/YOLOInventoryDetector.swift`: current generic YOLO static-image model loading and inference.
- `Inventory/Models/InventoryItem.swift`: inventory, detection, assistant event, motion, and export models.
- `Inventory/Stores/InventoryStore.swift`: local persistence, assistant snapshot, laptop review package.
- `Inventory/Views/ReviewDetectionsView.swift`: review/edit proposals before saving.

## Build Command

Use this from the repository root:

```sh
xcodebuild -project HomeInventory.xcodeproj -scheme HomeInventory -destination generic/platform=iOS -derivedDataPath ./DerivedData CODE_SIGNING_ALLOWED=NO build
```

If files are added outside existing project membership, regenerate with:

```sh
xcodegen generate
```

## Known Warnings

`Inventory/Support/PhotoCameraPicker.swift` builds but currently emits Swift 6 / AVFoundation actor-isolation warnings around capture session usage and high-resolution capture API deprecations. They are not the primary product blocker.

## Immediate Next Steps

- Continue live scan tuning around `YOLOView`.
- Keep the current generic live model only as a plumbing test.
- Export or bundle the correct inventory-capable Core ML model and point both static and live paths at it.
- Add stable object tracking across frames before creating inventory proposals automatically.
- Use mission/room only as context, never as a hard requirement for detection.
- Expand category keyword rules for metadata quality, but do not confuse those rules with model vocabulary.
